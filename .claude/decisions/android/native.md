# JNI bridge and build (android/native) Decisions

> Snapshot of current consensus. Evolution: `git log --grep="MODULE: android/native"`
>
> Last distilled: 2026-11-07 (HEAD = 2d78930). D1–D4 were seeded by hand from the retired design
> doc §11 and the round records in `docs/rounds/`, so their sources cite rounds; later entries cite
> commits.

## Active

### D1: Kernels cross JNI as handles into a table
- **What**: Kotlin holds a numeric handle; each call looks up the `Arc<Machine>` in a global table and clones it; `stop` and `shutdown` remove the entry, after which calls find nothing and return sentinels or throw.
- **Why**: The first design passed an `Arc` raw pointer and required Kotlin not to use it after `stop`; on a reset, the main thread closed a console after the worker had already freed the kernel and hung on a freed lock.
- **Tradeoffs**: Every call takes the table lock briefly.
- **Watch out**: Drop the table guard before dropping the last `Arc`, since `Machine`'s drop kills processes and joins threads: bind a removed or replaced entry and drop it after the statement, because a temporary is dropped while the statement's guard is still held.
- **Source**: rounds 07 (`07-m5`), 99 (`99-choose-rootfs`); 7f79758

### D2: The native library is always a release build; debug apps add test hooks and the borrow check
- **What**: cargo-ndk builds `arm64-v8a` in release for every variant; debug variants enable `test-hooks` (the bug-simulation syscall) and `borrow-check`.
- **Why**: The instrumentation tests need the hooks to simulate kernel and engine bugs inside the app process, and the release APK must not contain them (checked in the `.so`); the BKL borrow check, once debug-only, was made a feature so release builds can run it too.
- **Tradeoffs**: Rust debug assertions never run on Android.
- **Source**: rounds 07 (`07-m5`), 21 (`21-robustness-finish`), 89 (`89-release-borrow-check`)

### D3: The APK is arm64 only and ships its native library uncompressed
- **What**: minSdk 29, target 37, `arm64-v8a` only; `useLegacyPackaging = false` so the 16 KB-aligned library maps straight from the APK; the rootfs asset is named `rootfs.tgz`.
- **Why**: Only aarch64 hosts are supported (Tier 1 translates aarch64 to aarch64); NDK 29 aligns `LOAD` segments to 16 KB, so uncompressed storage works on 16 KB-page devices; AAPT would unpack an asset ending in `.gz`.
- **Source**: round 07 (`07-m5`)

### D4: Released sources are generated by a script, without running downloaded build code
- **What**: `scripts/release-sources` bundles Appine at a clean `HEAD`, the vendored crates, the aports directories plus checksum-verified upstream sources of the minirootfs's GPL packages, and the Ghostty release with the Zig packages its build fetches (D6).
- **Why**: Under GPLv3/AGPLv3 the APK must come with the complete corresponding source, including statically linked crates, and the bundled busybox, apk-tools and other GPL packages need their sources too; evaluating an APKBUILD's `source=` would mean running downloaded shell code, so the files are found through its `sha512sums` instead.
- **Tradeoffs**: Whether the repository is published or a written offer accompanies the APK is still the user's decision.
- **Source**: rounds 192 (`192-license`), 200 (`200-release-sources`); b38d29c

### D5: The JNI bridge, the build and release packaging are one module
- **What**: android/native holds `hosts/android` (except the vt.c/vt.rs terminal shim), `Native.kt`, the Gradle files, the manifest, the debug and instrumentation-test sources, `android/licenses` and the `fetch-ghostty` and `release-sources` scripts.
- **Why**: JNI, Gradle and the manifest had no map (§11 only touched on them), and `scripts/release-sources` fit neither harness nor android/setup, since it packages the sources the APK release must ship.
- **Tradeoffs**: `MachineTest` exercises every android module but is filed here; the module grew from the bridge and build to release packaging.
- **Watch out**: JNI `shutdown` still drops the last `Arc<Machine>` under the table lock, against D1, and panics outside the kernel's wrapped calls abort the app.
- **Source**: 12c4afa, 16ac7a2

### D6: libghostty-vt is built with Zig into every Android library and shipped with its notices and sources
- **What**: For Android targets build.rs runs `zig build -Demit-lib-vt -Dcpu=baseline -Doptimize=ReleaseFast` (Zig 0.17.0, proxy variables removed) on the Ghostty 1.4.0 source that `scripts/fetch-ghostty` downloads with a pinned sha256, and links libghostty-vt.a and vt.c statically into libappine.so; fetch-ghostty fetches only the Zig packages the build uses by running its configure phase with build.rs's options; the notices list Ghostty, uucode (with the Unicode and Hoehrmann licences), simdutf, Highway, Wuffs, Zig's compiler_rt and JetBrains Mono from copies in `android/licenses`.
- **Why**: libghostty-vt (android/terminal D5) is a Zig build that has to end up in libappine.so, and it could replace Termux in every build only once the notices and released sources (D4) covered it.
- **Tradeoffs**: Every Android build needs Zig 0.17.0 and a one-off fetch; only the sha256 is checked, the minisign signature by hand when upgrading; the licence copies and versions are kept by hand, and build.rs and fetch-ghostty must keep the same zig build options.
- **Watch out**: A Ghostty upgrade can change the C API silently (OPT_USERDATA changed meaning in 1.4), need a newer Zig and add linked components the notices miss (list libghostty-vt.a's objects again); Zig's HTTP client fails through some proxies; build.rs reruns only on vt.c, build.zig.zon and its environment variables.
- **Source**: 394aecf, b38d29c

### D7: Material Components is a direct dependency, with its licences allow-listed
- **What**: `com.google.android.material:material:1.14.0` is declared inline like androidx.core, and NoticesTask's Apache groups gain `com.google.android.material` and `com.google.errorprone:error_prone_annotations`, both POMs checked.
- **Why**: The Material 3 restyle needs Material Components on the classpath, and NoticesTask fails the build for any Android library outside the groups known to be Apache-2.0.
- **Tradeoffs**: AppCompat, androidx.activity and CoordinatorLayout are used but arrive only through Material, and versions are still bumped by hand.
- **Watch out**: A Material upgrade can bring a library outside the known groups, which stops the build until its licence is checked (as intended), and the APK's growth was not measured.
- **Source**: 55be399

### D8: Instrumentation tests cover oversized downloads, homeless accounts and repeated reads of saved tabs
- **What**: `downloadsAreVerified` expects a download one byte past its pinned length to fail with no partial file, `documentsWithoutAHomeDirectory` checks the roots and refused writes for a home of `/` and a missing home, and the saved-tabs test (its tabs built without names since 7c35183) reads the same tabs twice before the kernel is up and expects one content-named transcript per saved tab.
- **Why**: The fetch cap, homes of `/` and keeping the killed-run marker had no device-side coverage, and the saved-tabs test still expected the marker to be deleted.
- **Tradeoffs**: Only the `file:` URL path is exercised, not HTTP resumption, and loading an index written by a version with tab names is untested.
- **Watch out**: The saved-tabs test assumes transcripts are the only `.txt` files in `files/tabs`, and each home case needs its own login setting so the provider's cached home is not reused.
- **Source**: 544418f, 711b034, d5dbe29; 7c35183

### D9: `Native` and the JNI bridge follow a kernel's life
- **What**: `Native` runs init, the store, browsing, start, boot, `setRoutes`, the console functions, the poll's calls in poll order, `trimMemory`, shutdown and stop; hosts/android's JNI functions follow Native.kt's order with `MACHINES` opening the kernel section and the string and error helpers last; `MachineTest` is grouped by app flow without pinning JUnit's method order.
- **Why**: The user wanted each file to read in the order its code runs; Native's functions and MachineTest's tests followed neither a kernel's life nor the app's flow, and the bridge's helpers sat above the JNI functions using them.
- **Tradeoffs**: git blame on the moved lines points at these commits unless read with -M or an ignore-revs file; MachineTest's diff is large for no change in behaviour.
- **Watch out**: A function added to Native.kt goes to the same place in the Rust bridge.
- **Source**: a546fea, 55d75ac

### D10: Kotlin compiler and lint warnings fail the build
- **What**: `kotlin.compilerOptions.allWarningsAsErrors` covers every compilation, local builds included, and `lint.warningsAsErrors` is on with GradleDependency, AndroidGradlePluginVersion, OldTargetApi, ExpiringTargetSdkVersion and OutdatedLibrary informational, since they follow data outside the repository; no formatter, detekt or extraWarnings.
- **Why**: CI ran lintDebug without failing on its warnings and Kotlin warnings were ignored, while the Rust code is held to clippy `-D warnings`.
- **Tradeoffs**: A warning stops local builds too, unlike local cargo builds; outdated dependencies and target SDK deadlines fail nothing and must be noticed in the report; formatting stays manual.
- **Watch out**: Upgrading compileSdk, AGP, Kotlin or a library can surface new deprecations or checks as failures; Play SDK Index errors from outside data can still fail lint; an informational issue ID that a later AGP drops would be reported as unknown, now an error.
- **Source**: 4c1a3ce

### D11: Route lines with non-ASCII hex fields are skipped
- **What**: `parse_route` requires its hex fields to be ASCII and otherwise skips the route like any malformed one.
- **Why**: It sliced the fields by bytes, so a non-ASCII character would panic, and a panic in the JNI layer aborts the app.
- **Tradeoffs**: None.
- **Watch out**: Other unwrapped JNI code can still panic (D5's Watch out).
- **Source**: 09188ec

### D12: The APK bundles the newest Alpine tarball and doas package by version
- **What**: build.gradle.kts picks both with a `byVersion` comparator that compares the numbers in their names in order, as the scripts do (harness D20).
- **Why**: Lexical order picks the wrong release as soon as a minor version gains a digit, and the APK bundles whatever the build picks.
- **Tradeoffs**: None.
- **Watch out**: None known.
- **Source**: b014e84
