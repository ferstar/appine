# M9 之前：从外面转发进来的连接带上真实的客户端地址（2026-11-01）

← [M9 之前：过滤链（2026-11-01）](175-filter.md) · [索引](../milestones.md)

[第 173 轮](173-port-forwarding.md)的推迟项。从 appine 外面连到发布的端口时，宿主上的转发线程替容器接受连接，再连过去，连接时绑的是网关在宿主上的地址，所以容器看到的来源总是网关（与 docker-proxy 一样）。Linux 上外面的设备连发布的端口走的是 DNAT，容器看到的是客户端真实的地址：访问日志、按 IP 的限流、白名单都按它算。

## 做法

- **按连接分地址**（`core/kernel/src/forward.rs`）：
  - 宿主上 127.254.0.0/16 留给从外面转发进来的连接；新的网络命名空间分宿主地址段时不再取 127.254（原来只跳过开机时的命名空间用的 127.255）。
  - 转发线程接受的连接，客户端是 IPv4、不是回环地址时（别的设备；IPv4 映射的 IPv6 地址也算），从这一段里分一个地址，绑上它和客户端原来的端口（绑不上这个端口就让宿主选），再连容器。
  - 登记 (这个地址 → 客户端的地址、端口、绑上的宿主端口)，连接结束时去掉。登记表在进程里一份，转发线程写、内核层读。
- **换回真实地址**（`netns::from_host`）：任何命名空间里看到的对端是 127.254.x.y、端口也对得上时，换成客户端的地址和端口。所以容器里 accept、getpeername、`/proc/net/tcp` 报告的都是它。低端口映射不换这一段的端口。
- **回环地址的客户端照旧**：手机上别的 App、浏览器开 localhost 连进来时，照旧绑网关的地址。Linux 上从本机连发布的端口时 netavark 做 masquerade、docker 经由 docker-proxy，容器看到的也是网关。
- **UDP 的转发也照旧**：容器回给真实地址的数据报，要经由转发 socket 才回得去，地址映射里没有这个方向。

## 测试

- 单元测试新增 2 个：
  - `forward`：用宿主上一个不是回环的地址当外面的客户端连进来，转发的连接绑的是 127.254 的地址和客户端的端口，登记着客户端真实的地址；两边关掉之后登记没了；回环地址来的不算外面的客户端。
  - `netns`：127.254 的对端报告成登记的客户端地址，宿主端口对不上的不换。
- 实测：开发容器里后台起 appine，用 nftables 驱动的 podman 起 `-p 8080:80` 的容器，从开发容器的 eth0 地址（不是回环）连 8080。容器里 netstat 看到的对端是 `::ffff:172.17.0.2:43664`，就是客户端的地址和端口；原来是网关 10.88.0.1。
- cargo test（318 个）、clippy（含 Android）、格式、两层的全部差分测试（49 组）通过。LTP 的 syscall 测试 1011 个通过（上次 1012）：select02 睡得太久，单独重跑也连续失败；同时在原生容器里量 `select`，睡 10 ms 多 2.6 ms、睡 25 ms 多 2.7 ms，是 colima 虚拟机这段时间的计时器精度（第 171 轮遇到过），这一轮也没有改 select。
- 变异检查：转发线程不绑 127.254 的地址、`from_host` 不认这一段，分别被两个单元测试抓到。
  - 写这一轮时发现：只跑单元测试的变异检查，之前没在容器里先 touch 源文件，cargo 沿用了上一个变异时编的东西。补上之后才是各自的测试失败。前几轮用单元测试抓的变异，失败的都是对应的那个测试，不受影响。

**推迟项**：

- 只有 TCP、IPv4 的客户端。UDP、纯 IPv6 的客户端，容器看到的仍是网关。
- 绑客户端的端口失败时（这个 127.254 地址上不会有，宿主只是兜底）端口是宿主选的，与客户端的不同。
- 一个 127.254 地址只登记一个连接，连接结束就去掉；之后再连回这个地址的（容器主动连客户端）走宿主网络，不经过转发线程。
