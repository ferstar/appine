# M9 之前：被叫醒的进程在 /proc 里是 R（2026-10-28）

← [M9 之前：CPU 时间不倒退（2026-10-28）](80-cpu-times.md) · [索引](../milestones.md) · [M9 之前：测试自己的竞争和丢掉的现场（2026-10-28）](82-test-races.md) →

LTP 的 shmctl01 记在[已知的偶发失败](../milestones.md#已知的偶发失败)里，说明是"全量并发时子进程还没 `shmdt` 完就超时"。按时间排列保存下来的全量结果，它早期时好时坏，最近 11 次每次都失败，日志里多数不是超时：子进程 shmdt、父进程检查时 `shm_nattch` 还是 13（应该是 0），继承的那段也一样。

- **原因**：shmctl01 的 20 个子进程停在 `pause()` 里。父进程给它们各发一个 SIGUSR1，再用 `TST_PROCESS_STATE_WAIT` 轮询 `/proc/<pid>/stat`，等状态回到 S，就当子进程已经做完了下一步（shmat 或 shmdt），接着检查 `shm_nattch`。Linux 上 kill 返回之前，`signal_wake_up` 经由 `try_to_wake_up` 已经把被叫醒的进程改成可运行，状态是 R，直到它做完这一步、再进 pause 才回到 S。appine 的状态看的是线程的 `sleeping` 标记，它在线程等待时置上，被叫醒的线程重新拿到 BKL 之后才清掉。这中间状态还是 S，父进程马上就往下走，有的子进程还没跑起来。并发的负载越重，子进程起来得越慢，所以最近几乎每次都失败。
- **改动**：所有叫醒最后都落到等待线程自己的事件（eventfd）上，放开 BKL 时触发。`Task::asleep` 是 `sleeping` 置着、并且事件还没触发；事件已经触发、线程还没清掉它时就是"被叫醒了还没跑起来"，`/proc/<pid>/stat`、`status` 等报告 R。hal 的 `Event` 加了不清除状态的 `is_signaled`（零超时的 poll）。平均负载、OOM 检查、挑接收信号的线程仍然只看 `sleeping`。
- **测试**：
  - 差分测试 compat 组加了 `woken.c`：8 个子进程停在 `pause()` 里，每轮父进程照 LTP 的做法发 SIGUSR1、等它们的状态回到 S，检查每个子进程都已经做完这一轮的计数，共 20 轮。两层各跑 3 次都与原生相同（都是 0 次）；上一轮的二进制 3 次分别有 42、67、71 次（共 160 次）子进程还没跑起来就被当成又睡下了。
  - LTP 的 shmctl01 和 shm、msg、sem 的 30 多个测试一起并发跑：上一轮的二进制 3 次都失败，其中一次卡到 LTP 自己的超时（父进程把还没跑起来的子进程当成已经睡下，提前发了下一个 SIGUSR1，信号在子进程进 `pause()` 之前就处理掉了，子进程之后一直停在里面）；改动之后 3 次都通过。
  - hal 的单元测试新增 `checking_an_event_does_not_clear_it`。cargo test（207 个）、clippy（含 Android）、两层的 20 组差分测试通过。LTP 的 syscall 测试 959 个通过（上一轮 958），多出来的是 shmctl01，其余逐项相同。

**推迟项**：

- 被叫醒的线程在平均负载里仍算作睡着，直到它拿到 BKL。
