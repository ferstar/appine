# M9 之前：独占的唤醒（2026-10-27）

← [M9 之前：嵌套 epoll 的边沿（2026-10-27）](47-nested-epoll.md) · [索引](../milestones.md)

[epoll 的边沿](42-epoll-edges.md)那一轮让 `EPOLLEXCLUSIVE` 的一个边沿只报告给一个 epoll，但等待的线程仍然都被叫醒：几个进程各用一个 epoll 等同一个监听 socket，来一个连接，宿主 poll（TCP）或者文件类的广播（AF_UNIX）把每个等待者都叫醒，没轮到的在内核里重新检查之后接着睡。Linux 每次唤醒只叫醒一个独占的等待者，别的根本不醒。这一轮做到同样（§10）。

- **能看到"有没有醒"**：`/proc/<pid>/status`（和线程的）的 `voluntary_ctxt_switches`、`nonvoluntary_ctxt_switches` 原来总是 0，现在取宿主线程的（`appine_hal::thread_ctxt_switches`，减去线程开始时的值，宿主线程会被复用）。宿主线程每睡下一次就是一次自愿切换，没被叫醒的线程不变，原生上也是这样，所以差分测试可以数"被叫醒过的进程"。量下来原来是返回 1 个、被叫醒 3 个，原生是 1 个、1 个。
- **独占门**（`ExGate`）：等待时不自己等独占关注的文件，而是把自己登记在这个文件的门上（`Kernel::ex_gates`，按先后）；等完再去掉。定时器线程替它们看（`check_exclusive`，照 `O_ASYNC` 的做法：有门时它登记在所有通道上，任何修改都叫醒它，宿主 socket 新到的数据从 42 轮的宿主 epoll 看，与它的其他宿主 fd 一起等）：门上的数据代数变了、文件就绪、而且这个边沿还没被哪个 epoll 报告过（`exclusive_claim`）时，只叫醒排在最前面的一个，把它从门上取下。被叫醒的那个检查时认领这个边沿、报告给程序。宿主 fd 建不了记录新数据的宿主 epoll 时（宿主 stdio 是普通文件），门看不到它上面的事件，这种关注仍像 42 轮那样自己等。
- **只等独占关注的等待者**：epoll 里只有独占的关注时，epoll_wait 不再登记在文件类的唤醒里（`Cx::wait_on` 的通道为 0），别的文件上的修改不叫醒它；`epoll_ctl` 原来靠文件类的唤醒叫醒正在等的线程，现在直接叫醒等这个 epoll 的线程（`Epoll::waiters`）。epoll 里还有进程内的别的文件（管道、eventfd、AF_UNIX 连接）时照旧登记，那是 poll、epoll 的等待者共用一个通道的整体设计（[futex 定向唤醒](16-futex-targeted-wake.md)起的推迟项），与独占无关；宿主 socket 照旧自己等。
- **出错时**：定时器线程处理独占门时撞上内核层的 bug，叫醒所有门上的等待者再去掉这些门，宁可多叫醒。
- **性能**：Go 的 HTTP 回环（不用 `EPOLLEXCLUSIVE`）与改动之前的二进制交替跑三次：keep-alive 83–91 对 82–86 微秒，新连接 198–217 对 195–210 微秒，在噪声范围内。
- **测试**：差分测试 `epoll` 的独占用例改为同时数从 epoll_wait 返回的进程和被叫醒过的进程（自愿切换的次数变了），AF_UNIX、TCP 监听 socket 都是 1、1，两个执行层连跑几次都与原生相同。变异检验：保留上下文切换的统计、只关掉独占门，是返回 1、叫醒 3。单元测试新增独占门一个边沿只取一个等待者、报告过的边沿不叫醒、下一个边沿轮到下一个。
  - cargo test（189 个）、clippy、Android clippy、两层的 17 组差分测试通过。LTP 的 syscall 测试 957 个通过，与上一轮相同：select02 这次通过，shmctl01 这次失败，都是[偶发项](../milestones.md#已知的偶发失败)。
  - 上面的全量运行之后补上了宿主 fd 建不了宿主 epoll 时的回退，重新构建后又跑了两层的 `epoll` 组（通过）和 LTP 的 epoll 测试。这时虚拟机的计时延迟偏大（原生的 nanosleep 1 毫秒量出 1.5 毫秒、10 毫秒量出 13.3 毫秒），epoll_wait02、epoll_pwait03 和 nanosleep01 连续失败，[ptrace 的第二步](41-ptrace-gdb.md)的二进制同样失败、量到的时间相同，其余 epoll 测试与全量运行相同。

**推迟项**：

- epoll 里还有进程内的别的文件时，等待者仍被所有文件类的修改叫醒（poll、epoll 的等待者共用一个通道，[futex 定向唤醒](16-futex-targeted-wake.md)起的推迟项）。
- 有独占门时定时器线程被每一次文件类的修改叫醒，与有 `O_ASYNC` 的文件时一样。
- 门上被叫醒的等待者还没来得及认领时又来了一个边沿，会再叫醒一个；后一个发现边沿已经被认领就接着睡，不像 Linux 那样也去处理（水平触发时由认领的那个接着报告）。
