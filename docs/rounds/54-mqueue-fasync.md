# M9 之前：消息队列和信号驱动的 I/O 不再叫醒所有人（2026-10-27）

← [M9 之前：锁和宿主 socket 只叫醒等它们的线程（2026-10-27）](53-locks-host-sockets.md) · [索引](../milestones.md) · [M9 之前：宿主 stdio 上的阻塞读只等宿主 fd（2026-10-27）](55-host-stdio.md) →

[上一轮](53-locks-host-sockets.md)留下的推迟项：关闭 POSIX 消息队列，以及程序在设了 `O_ASYNC` 的文件上读数据，仍请求整个文件类的通道，叫醒所有 poll、epoll 的等待者。消息队列的收发更是请求所有通道（[按对象唤醒](49-targeted-wakeups.md)、[起进程和设定时器](51-spawn-timer-wakeups.md)的推迟项），连等子进程的 shell 也被叫醒。上一轮的微基准（`target/herd/sockherd.c`）加了三项，8 个空等的进程，epoll 和 recv 两种空等方式各量两次，每次操作的微秒数和空等的进程被叫醒的次数：

| 操作 | 原生 | 之前 | 之后 |
|---|---|---|---|
| 消息队列发一条再收一条 | 0.5 | 18.8–21.4（每次叫醒 5.1–6.1 次） | 0.3（0 次） |
| 打开再关闭消息队列 | 0.7–0.8 | 4.9–9.8（1.9–2.5 次） | 0.3–0.4（0 次） |
| 设了 `O_ASYNC` 的管道写 1 字节再读出 | 0.5 | 3.4–13.6（1.9–3.2 次） | 1.4–2.1（0 次） |

`O_ASYNC` 那一项剩下的是每次读都叫醒定时器线程重新检查。

- **消息队列按对象唤醒**：poll、epoll 登记消息队列对象，阻塞的 mq_timedsend、mq_timedreceive 只等这个队列，收发只请求这个队列。`SIGEV_THREAD` 的通知请求那个 netlink socket（musl 用一个 netlink socket 和阻塞在 recv 里的线程实现它）。关闭消息队列不再叫醒谁：没有线程在等它关闭，阻塞的收发拿着打开文件，与 Linux 一样不因别人关闭 fd 而醒。
- **信号驱动的 I/O 只叫醒定时器线程**：在设了 `O_ASYNC` 的文件上读到数据、用完数据时，原来请求整个文件类的通道，为的是让定时器线程重新检查（`check_fasync`），现在直接叫醒定时器线程（`Shared::timers`）。设置 `O_ASYNC` 时也直接叫醒它：没有 `O_ASYNC` 的文件时它只听"其余"通道，原来要等它因为别的事醒来才开始检查新登记的文件，有 guest 线程在运行时最多晚 20 毫秒。
- 至此，没有修改再整个请求文件类的通道了（`request_wake_files` 删掉了），打开文件上的修改都按对象请求。还会叫醒所有听这个通道的等待者的，只剩请求所有通道的修改：所有线程都屏蔽的信号、SysV IPC、AIO 完成、SIGCONT、关闭控制台。
- **效果**：见上表。标准基准与上一轮的二进制交替各跑两次，都在噪声范围内：shell 0.23–0.24 秒对 0.24 秒，gcc 2.20–2.23 对 2.20–2.36，python 1.33–1.35 对 1.35–1.36，go build 5.93–6.06 对 5.99–6.11，Maven、Gradle 的热构建 5.88–5.95、1.31–1.38 对 5.82–5.92、1.34–1.37（前面是这一轮）。
- **测试**：差分测试 `wakeups` 的空闲部分加了两个空等的进程：一个阻塞在 mq_receive 里，一个 poll 自己的消息队列。别的进程的动作加了：收发别的消息队列 200 次、打开再关闭 50 次，读写设了 `O_ASYNC` 的管道 200 次。

  叫醒部分加了 5 项：
  - mq_receive；
  - poll 消息队列；
  - 队列满了之后的 mq_send；
  - `SIGEV_THREAD` 的通知；
  - 设了 `O_ASYNC` 的 TCP 连接读空之后，再来的数据也发 SIGIO。

  变异检验：
  - 上一轮的二进制上，12 个空闲的进程都被叫醒；
  - poll 不登记消息队列：poll 消息队列那一项等不到；
  - 通知时不请求 netlink socket：`SIGEV_THREAD` 那一项等不到；
  - 收发时不请求队列：mq_receive、poll、写满之后的 mq_send 三项等不到。

  去掉读数据、用完数据时直接叫醒定时器线程测不出来，与[起进程和设定时器](51-spawn-timer-wakeups.md)那一轮一样：最后一个线程睡下之后，定时器线程还会按排好的时刻再醒一次（查内存上限），顺带重新检查，SIGIO 最多晚 20 毫秒。
  - cargo test（192 个）、clippy、Android clippy、两层的 18 组差分测试通过。LTP 的 syscall 测试 957 个通过，与上一轮逐项相同。

**推迟项**：

- 有 `O_ASYNC` 的文件或者 `EPOLLEXCLUSIVE` 的独占门时，定时器线程仍被每一次修改叫醒（[独占的唤醒](48-exclusive-wakeup.md)的推迟项），在设了 `O_ASYNC` 的文件上每读一次也叫醒它一次。
